# EZagent Spec 生产就绪加固设计

日期：2026-08-22  
状态：用户已确认，进入实施

## 1. 目标与范围

本轮只处理审查中影响投入使用判断的三项缺口：修通私密漏洞报告渠道、加固 GitHub 发布与供应链治理、补充真实 Codex 宿主行为验收。项目功能范围、工作流语义、专家目录和现有静态激活规则不在本轮修改。

成功标准是：安全研究者可以实际提交私密报告；`main` 和发布标签具有适合单维护者仓库的防误操作保护；依赖与秘密风险由 GitHub 和 CI 持续检查；发布前能够在真实 Codex CLI 中复现并记录插件发现、初始化和路由行为，而不是只依赖源码断言。

## 2. 已确认决策

- 采用“单人维护保护”，不要求第二名维护者批准 PR。
- 所有正常修改通过 PR 进入 `main`，macOS 与 Windows 验证必须通过。
- PR 不要求批准人数，但未解决的审查对话必须先处理。
- 禁止删除 `main`、禁止强推，仓库管理员保留紧急绕过权。
- 公开用户仍只能 Fork 和提交 PR；只有获授写权限的协作者可以写入仓库。
- `v*` 发布标签一经创建不得删除或改写；从下一版本开始使用签名的 annotated tag。已发布且未签名的 `v0.1.0` 不改写。
- 真实 Codex 宿主验收作为发布门单独执行，不放进每次 PR 的确定性 CI，也不把模型输出伪装成稳定单元测试。

## 3. 私密漏洞报告

启用 GitHub Private Vulnerability Reporting，并保留 `SECURITY.md` 中的私密报告链接作为主入口。文档增加以下承诺与边界：

- 支持版本与报告范围；
- 首次确认和后续状态更新的目标时限；
- 报告应包含的复现信息；
- 在修复或协调披露前不要创建公开 Issue；
- 如果 GitHub 页面不可用，可通过仓库 Discussions 或普通 Issue 仅报告“私密通道不可用”，不得附带漏洞细节。

本轮不公开推断或新增个人邮箱。这样既避免暴露未经确认的联系方式，也保证主报告通道本身可用。

## 4. GitHub 发布与供应链治理

### 4.1 `main` 分支规则

使用 GitHub repository ruleset 保护默认分支：

- 目标为默认分支；
- 要求通过 PR 合并；
- 批准人数为 0；
- 要求解决所有审查对话；
- 要求分支与最新 `main` 同步；
- 要求 `Verify (macos-latest)` 与 `Verify (windows-latest)` 两个状态检查通过；
- 禁止删除和非快进更新；
- 管理员可在事故恢复时绕过，并由 GitHub 审计记录保留痕迹。

规则启用前先确认远端已有同名成功检查，避免因状态名称错误锁住合并。

### 4.2 发布标签规则

为 `refs/tags/v*` 建立 active ruleset，阻止删除和更新。现有 `v0.1.0` 保持原对象不变，以免破坏已发布安装引用。

发布文档要求未来版本使用签名 annotated tag，并在推送前本地执行 `git verify-tag`。标签保护负责不可变性；签名负责来源证明，两者不可互相替代。由于仓库当前没有可供 CI 信任的维护者公钥，本轮不在 CI 中添加会永远失败或被轻易绕过的签名检查。

### 4.3 持续安全检查

GitHub 侧启用：

- Secret Scanning；
- Push Protection；
- Dependabot security updates；
- GitHub 支持时启用 secret validity checks 与 non-provider pattern 扫描。

仓库增加 `.github/dependabot.yml`，每周检查 npm 依赖并限制同时打开的 PR 数量。CI 在 `npm ci` 后执行 `npm audit --audit-level=high`，阻止 high/critical 已知漏洞进入受保护分支。

不引入新的第三方 Secret Scanner Action。秘密检测由 GitHub 原生能力完成，避免为了扫描秘密再扩大 Actions 供应链。

## 5. 真实 Codex 宿主验收

### 5.1 分层策略

现有 `test/codex/activation-contract.test.ts` 继续验证静态契约和关键文案。新增的宿主验收验证真实 Codex CLI 是否发现已安装插件并按预期响应。两者职责分开：

- 静态测试：快速、确定、每次 CI 执行；
- 宿主验收：真实模型与插件运行时、可能消耗网络和模型额度、发布前执行并记录证据。

### 5.2 验收语料与执行器

新增版本化的 JSON 验收语料，覆盖：

- 明确初始化；
- 隐式初始化请求；
- 未初始化项目中的普通开发请求；
- 已初始化项目中的直接专家请求；
- 间接专家请求；
- 负向与边界请求；
- 同一任务内的后续请求。

新增 TypeScript 执行器，通过 argv 数组调用当前机器上的 `codex`，不拼接 shell 命令。执行器只在操作者显式运行时启动，启动前检查 Codex 版本、插件安装状态和 Git 工作树状态；每个场景使用独立临时项目，避免修改本仓库或真实业务项目。执行结果写入被忽略的本地 evidence 目录，包含 Codex 版本、插件版本、被测提交、操作系统、场景结果和必要的脱敏 transcript 摘要。

执行器不自动安装插件、不修改 Codex 全局配置、不自动提交或推送。缺少插件、网络或认证时明确失败并给出准备命令。

### 5.3 判断与发布门

行为结果同时使用机器可检查的不变量和人工复核：

- 机器检查确认命令退出状态、场景完整性、临时项目是否出现预期/非预期的 EZagent 状态变更，以及证据元数据是否绑定当前提交；
- 人工复核确认 Router 是否在正确场景出现、是否在负向场景保持静默、是否在需要授权时先请求确认，以及专家选择是否符合请求语义。

发布清单要求所有场景通过，并保存脱敏证据摘要。PR CI 只验证语料 schema、执行器单元测试和发布清单契约，不调用真实模型。

## 6. 实现与测试策略

代码行为使用测试驱动开发：先为宿主验收语料解析、命令参数构造、临时目录隔离、证据校验和错误处理编写失败测试，再实现最小执行器。配置和文档通过契约测试验证关键字段，避免 GitHub 设置与仓库声明再次漂移。

本地验证门为：

```bash
npm audit --audit-level=high
npm run plugin:verify
npm run verify
git diff --check
```

GitHub 外部状态在写入后重新读取并逐项核对：Private Vulnerability Reporting、Secret Scanning、Push Protection、Dependabot security updates、分支 ruleset 和标签 ruleset。设置 API 若因账户套餐或 GitHub 限制拒绝，停止声称该项完成，并记录可执行的替代方案。

## 7. 失败处理与回滚

- ruleset 创建前读取现有规则，避免重复或覆盖用户已有配置；新规则导致锁定时只停用本轮创建的 ruleset，不删除其他规则。
- GitHub 安全开关若部分成功，报告每一项实际状态，不把部分成功描述为全部完成。
- CI 审计因注册表暂时不可用时保持失败，重试后再判断；不得把网络错误解释为“无漏洞”。
- 宿主验收失败时保留脱敏证据和临时目录位置，不修改产品规则来迎合一次随机输出；先区分稳定缺陷、环境问题和模型波动。
- 不改写 `v0.1.0`，不重写 Git 历史，不删除现有分支、标签或 GitHub 配置。

## 8. 非目标

- 不邀请或自动授予新的 GitHub 协作者权限。
- 不要求项目所有者批准自己的 PR。
- 不发布 npm 包，不创建新 Release，不重签或移动 `v0.1.0`。
- 不把个人邮箱写入公开安全文档。
- 不在普通 PR CI 中调用付费或非确定性的真实模型。
- 不修复本轮三项之外的审查建议。

## 9. 验收标准

- GitHub 私密漏洞报告页面实际可提交，`SECURITY.md` 不再指向关闭的功能。
- 外部贡献者不能直接写入仓库，只能通过 Fork/PR 提议修改。
- `main` 的正常合并必须经过 PR 和两个平台 CI，但不需要第二名审批者。
- `main` 和 `v*` 标签不能被普通写入者删除或强制改写，管理员保留可审计的紧急绕过。
- Secret Scanning、Push Protection 和 Dependabot security updates 的远端状态为 enabled。
- Dependabot 配置有效，CI 会阻止 high/critical npm 漏洞。
- 真实宿主验收语料、执行器、证据格式和发布清单齐全；至少一次针对当前版本的真实 Codex 验收结果可追溯。
- 完整本地测试、构建、插件验证与差异检查通过，GitHub 规则重新读取后与本文一致。
